## 1. 重构目标

本次工作不是在现有完整工程上继续堆叠功能，也不是一次性生成整套 H 题代码，而是重新建立一条：

1. 以 2026 年 H 题官方要求为唯一项目目标；
2. 以实物、准确版本的原理图和经过确认的实测结果为硬件真值；
3. 先完成资料体系和硬件约束，再逐步增加代码；
4. 当前只保留 C07A 纯循迹能力；
5. 每加入一个新硬件或功能，都经过单独确认、接线、实现和验收；
6. Agent 能快速读取资料，并能区分已确认事实、推导结论和待实测项目

的干净开发分支。

重构完成后，仓库应同时满足：

- **代码小而确定**：当前固件只有循迹，不提前混入 D36A、K230、球杆控制或完整赛题流程。
- **资料广而完整**：最终赛题计划使用的硬件已经完成选型、资料阅读和 AI 可读化整理。
- **事实可追溯**：每条关键硬件结论都能追溯到实物、原理图、厂家手册、赛题原文或实测记录。
- **冲突不猜测**：出现版本、引脚、接线或实测冲突时，由用户确认后才能冻结结论。
- **历史可恢复**：`main`、现有标签和当前未提交成果均不因重构丢失。

### 2.1 当前循迹代码的处理原则

第一步不是改写该标签中的算法，而是把它当作不可变的来源快照：

- 先记录标签、提交、文件清单和源码哈希；
- 初次迁移保持源码行为不变；
- 将它依赖的 BSP、SysConfig 和构建文件拆成真正独立的循迹工程；
- “迁移”和“优化”必须分成不同提交；
- 在干净环境中重新构建并运行现有仿真测试后，才允许开始后续优化；
- 编码器、速度环和诊断代码是否继续属于最小循迹工程，以该标签的实际行为和后续用户决定为准，不在迁移时擅自删除。

### 2.2 硬件资料与代码范围不对称

“暂时不写某硬件代码”不等于“不整理该硬件资料”：

- C07A、模块化控制器、D103A/TB6612、循迹传感器等资料用于当前工程；
- D36A、步进电机、MS42CG、K230、摄像头和供电资料用于未来阶段准备；
- 未来硬件可以写清电气要求、接口能力、风险和待实测项；
- 在进入对应开发阶段前，不为未来硬件随意占用 MSPM0 引脚，也不建立空壳驱动。

## 3. 执行原则

### 3.1 真值优先级

在不存在待用户裁决冲突时，采用以下优先级：

1. 当前实物丝印、连线和可重复的仪器/实车结果；
2. 与实物版本完全匹配的原理图、资源表和数据手册；
3. 同版本厂家手册及官方例程；
4. 用户明确确认的采购型号和系统决策；
5. 购买页面、开源仓库和第三方资料；
6. 旧项目文档和历史代码；
7. Agent 推导。

任何高优先级证据与已有结论冲突时，不自动覆盖，而是建立冲突条目并询问用户。

### 3.2 文档先于代码

只有以下信息已经明确，才能为一个硬件写正式驱动：

- 精确型号和板卡版本；
- 供电、电平和最大额定值；
- 接口及连接器定义；
- 启动、复位和失效安全状态；
- 所需 MCU 外设和引脚；
- 与现有资源的冲突；
- 最小台架验收方法。

### 3.3 分阶段，不跨阶段补全

- 每个阶段只完成该阶段的交付物。
- 阶段验收未通过，不进入下一阶段。
- 发现未来需求时只登记待办，不提前生成实现。
- 每轮向用户报告：完成内容、证据、改动文件、未决问题和下一步。

### 3.4 原始资料与 Git 体积控制

当前厂家资料包体积约为：

- WHEELTEC C07A 资料：约 3.57 GB；
- D36A 资料：约 293.5 MB；
- 正点原子 DNK230D 资料：约 1.30 GB。

这些资料不得整包直接提交 Git。采用以下策略：

- Git 内保存资料索引、版本、来源、原始路径/网址、文件大小、SHA-256、许可情况和阅读状态；
- Git 内保存经过核对的 Markdown、CSV、引脚表、网络表和必要的小型示意图；
- 2026 H 题官方 PDF及少量关键原件是否入库，先检查版权、大小和必要性；
- 大型 SDK、视频、压缩包、构建产物和重复手册保留在 Git 外；
- 如果以后确需跟踪大型二进制，再单独评估 Git LFS，不在本次默认启用。

## 5. 分阶段实施计划

### 阶段 0：保护现状并建立隔离开发环境

#### 目标

在不影响当前脏工作树和 `main` 的前提下，为重构建立独立环境。

#### 操作

1. 记录真实 Git 根、远程、全部分支、标签和提交关系。
2. 保存当前 `git status`、已跟踪差异清单和未跟踪文件清单。
3. 对重要未提交内容制作只读备份或补丁；不执行 `clean`、`reset` 或覆盖式切换。
4. 验证标签：
   - `c07a-line-tracker-preferred-20260731`
   - commit `0ef4fe0ac1f4fc11c8abcb3771d886cda78e2f65`
5. 推荐从该标签建立普通历史分支 `refactor/h2026-docs-first`。
6. 使用 D: 盘上的独立 Git worktree 开发，不在当前脏工作树中切分支。
7. 将用户确认后的本计划书作为新分支第一个仅文档提交，使后续阶段都能按同一计划执行。
8. 若用户明确要求完全无共同历史，再另行评估 orphan 分支；本计划默认不使用。

#### 交付物

- 基线清单；
- 当前工作树保护报告；
- 新分支和独立 worktree；
- 标签文件清单及源码哈希。

#### 验收门 G0

- `main` 指针未变化；
- 当前未提交文件内容未变化；
- 新工作树干净；
- 新分支能追溯到已确认标签。

### 阶段 1：确认全项目硬件清单和精确版本

#### 目标

先回答“最终计划用什么”和“当前车上实际装了什么”，不在型号未定时整理错误资料。

#### 硬件状态分类

每项硬件必须属于以下一种：

- `CURRENT_INSTALLED`：当前循迹车已安装并使用；
- `CURRENT_PRESENT_UNUSED`：开发板/底板上存在，但当前代码不使用；
- `FUTURE_CONFIRMED`：H 题后续确定会使用，当前未接入；
- `CANDIDATE`：仍在比较，不能写入冻结方案；
- `REMOVED`：已拔除但需要记录冲突原因；
- `OBSOLETE`：不再用于新分支；
- `PENDING_IDENTIFICATION`：缺少丝印、版本或实物证据。

#### 清单字段

- 厂商、完整型号、硬件版本、丝印；
- 数量、采购状态、安装状态；
- 在 H 题中的用途；
- 电源和接口；
- 对应原始资料；
- 当前是否有实物照片；
- 已确认事实、待实测项和冲突编号；
- 是否允许进入当前接线表或代码。

#### 首批必须确认

1. C07A 核心板版本；
2. S27F/S28A 模块化底板的实际丝印；
3. D103A/TB6612 当前左右轮物理通道；
4. 当前安装的循迹模块及版本；
5. D36A 实物硬件版本；
6. 步进电机和 MS42CG 完整型号；
7. 最终 K230 是 01Studio CanMV K230，还是正点原子 K230D BOX；
8. 摄像头型号和排线接口；
9. 电池、稳压、保险和供电分配现状。

#### 交付物

- `docs/hardware/HARDWARE_INVENTORY.md`；
- 实物证据索引；
- 首版未决问题表。

#### 验收门 G1

- 不再使用“S27F/S28A”“K230 某版本”等模糊写法描述冻结硬件；
- 每个未来硬件都有确定、候选或待确认状态；
- 冲突项已向用户提问，未确认项未进入正式接线和代码。

### 阶段 2：完整阅读并体系化整理硬件资料

#### 目标

对已确认或明确列为候选的硬件完成一次系统化资料阅读，生成可供 Agent 快速使用的技术文档。

#### 2.1 建立资料索引

每个原始文件登记：

- 资料 ID；
- 硬件及版本；
- 文件名和资料标题；
- 厂家/作者；
- 发布日期或版本号；
- 本地原始路径和公开网址；
- 文件大小和 SHA-256；
- 文件类型、页数和是否有文本层；
- 许可/再分发状态；
- 阅读状态；
- 派生文档；
- 已知过期或冲突说明。

#### 2.2 C07A 和模块化控制器文档

至少覆盖：

- C07A 核心板准确版本；
- S27F/S28A 准确底板版本；
- D103A/TB6612；
- P03B；
- BLS、LED、MPU6050、外接 OLED；
- 当前 CD4051 八路灰度模块；
- 编码器接口、调试 UART、SWD 和定时器资源；
- 连接器、供电域、电平、默认上下拉和上电状态；
- 与当前纯循迹标签实际使用资源的对应关系。

输出必须包括：

- 模块关系图；
- 连接器引脚表；
- MCU 引脚到模块网络映射；
- 电源域和危险电压说明；
- 定时器/ADC/I²C/UART 资源表；
- 版本差异表；
- 当前循迹所需最小资源；
- 待实测项目。

#### 2.3 D36A 技术文档

至少覆盖：

- 实物版本与 V1.0/V1.1 原理图差异；
- `STEP`、`DIR`、`EN` 的接口、电平、极性和上电状态；
- 输入频率、脉宽和时序限制；
- 细分、限流和拨码真值表；
- 2025-07 与 2026-06 手册修订差异；
- 电机供电、逻辑供电、接地、保护和散热；
- 故障状态；
- 与 MS42CG 闭环方案的边界；
- 厂家例程中可复用和不可照搬的部分；
- 当前与 TB6612/C07A 引脚的冲突。

此阶段只输出技术约束和未来接口需求，不分配正式 MSPM0 引脚，不写驱动。

#### 2.4 K230 技术文档

先解决实际板卡型号，再只针对正确硬件整理：

- SoC 和板级版本；
- 内存容量；
- 摄像头接口和 GC2093 版本；
- GPIO/UART 引脚及电平；
- 供电入口、峰值负载、散热和启动过程；
- 板载 Wi-Fi、视频编码和 RTSP 能力；

- 两小时联合压力测试需要记录的指标。

此阶段不编写球识别、串口状态协议或 RTSP 业务代码。

#### 2.5 原理图 AI 可读化标准

对每套关键原理图至少生成：

1. 原理图版本和页码索引；
2. 关键器件表；
3. 连接器引脚表；
4. 关键网络表；
5. MCU 引脚复用表；
6. 电源树；
7. 上拉、下拉、分压、保护和默认状态表；
8. 跨页网络引用；
9. 与当前实物/代码的差异；
10. 未确认项。

结构化结果必须人工对照原图复核，不能把 OCR 或图像识别结果直接当真值。

#### 交付物

#### 验收门 G2

### 阶段 3：逐页整理 2026 年 H 题官方要求

#### 目标

将官方 PDF 转换为项目的最高层需求基线。

#### 操作

1. 对 4 页官方 PDF 直接提取文本层。
2. 按页对照原 PDF，检查上下标、单位、图号、尺寸、时间和条件。
3. 逐条整理：
   - 题目任务；
   - 系统组成；
   - 基本要求；
   - 发挥部分全部 5 个问题；
   - 评分和扣分条件；
   - 尺寸、材料、运动范围和时间限制；
   - 显示、录像、回放及现场操作要求；
   - 明示禁止项；
   - 图中隐含的几何和流程约束。
4. 为每条要求分配稳定 ID。
5. 建立“要求 → 硬件 → 软件 → 测试 → 当前状态”的追踪矩阵。
6. 对可能存在多种解释的句子保留原文短引和页码，建立待裁决项。

#### 交付物

- `docs/requirements/H2026_OFFICIAL_REQUIREMENTS.md`；
- `docs/requirements/REQUIREMENT_TRACEABILITY.md`；
- 官方图示的结构化说明；
- 五个问题的独立验收条目。

#### 验收门 G3

- 4 页内容逐页核对完成；
- 5 个问题无遗漏；
- 所有数值、单位、条件和评分项均可追溯到页码；
- 实施方案中的每项功能均能对应官方要求，不能以旧方案反推赛题。

- 方向；
- 电压；
- 默认状态；
- 当前所有者；
- 状态；
- 证据；
- 实测日期。

#### 验收门 G4

- 原理图、实物、代码和接线表四方一致；
- 左右电机通道和编码器符号由用户/实车确认；
- 无重复占用；
- 未接入硬件没有伪造的正式引脚分配；
- 按表可完成一次逐线复核。

### 阶段 5：建立干净仓库并迁移纯循迹代码

#### 目标

在资料真值完成后，将新分支整理为“只有纯循迹代码”的可构建项目。

#### 操作顺序

1. 先提交文档体系，不改循迹行为。
2. 从已确认标签按文件清单迁移纯循迹源码。
3. 将 line tracker 从 `h2026_q2` 中借用的 BSP、SysConfig 和构建依赖拆出。
4. 先生成逐路径 `KEEP`、`MOVE`、`REMOVE` 清单；存在用途或真值冲突的路径经用户确认后再处理。
5. 删除或归档新分支中的旧完整架构、K230/OpenMV 代码、旧 H 题实现和无关模块。
6. 清理构建产物、异常文件、缓存和临时脚本。
7. 建立最小 `.gitignore`。
8. 在 ASCII 路径的干净环境完成构建。
9. 运行已有仿真/主机测试。
10. 对照标签检查算法常量、方向、状态机和输出限制，证明迁移未改变行为。

#### 提交拆分

- `docs: establish hardware and requirement baseline`
- `chore: establish clean line-tracker tree`
- `refactor: make line tracker BSP self-contained`
- `test: verify migrated line tracker`

不得把“搬文件、删旧模块、改控制算法”混在一个提交中。

#### 交付物

- 独立的 `firmware/line_tracker`；
- 最小 BSP/SysConfig；
- 可重复构建命令；
- 仿真/主机测试；
- 基线迁移对照报告；
- 删除/归档清单。

#### 验收门 G5

- 新分支中的业务代码只有循迹；
- 不依赖已删除的 `h2026_q2` 或旧通用工程；
- 从干净检出可以构建；
- 现有测试通过；
- 迁移阶段没有未经批准的算法变化；
- 构建产物和大文件不在 Git。

### 阶段 6：建立 Agent 开发契约

#### 目标

让后续 Agent 每次进入项目时都能快速找到真值、知道当前阶段，并避免自动补全未来功能。

#### README 只回答

- 这个项目为什么存在；
- 当前实现到哪一步；
- 当前唯一可运行代码是什么；
- 如何构建和验证；
- 下一阶段是什么；
- 哪些内容明确尚未实现。

#### AGENTS.md 强制约束

- 必读文档顺序；
- 当前硬件真值入口；
- 当前允许修改的代码范围；
- 冲突和待实测处理方式；
- 禁止使用的旧模块/旧 SysConfig；
- 构建、测试和实车验收要求；
- 不得提前实现未来阶段；
- 变更硬件时必须同步更新哪些文档。

#### 验收门 G6

向一个没有历史上下文的 Agent 提供仓库后，它能够正确回答：

1. 当前只在做什么；
2. 当前没有做什么；
3. 实际硬件是什么；
4. IO 真值在哪里；
5. H 题五问在哪里；
6. 修改前要运行什么测试；
7. 遇到冲突时应停止并询问什么。

### 阶段 7：后续功能按单硬件切片逐步增加

该阶段不在本次基础重构中实现，只定义以后遵守的节奏。

每个新功能必须走完整闭环：

1. 用户批准进入该硬件阶段；
2. 复核实物型号；
3. 解除对应待确认项；
4. 更新 IO 和接线；
5. 完成独立台架程序；
6. 完成驱动和主机测试；
7. 完成实物验收；
8. 再接入主循迹工程；
9. 更新需求追踪矩阵。

建议未来顺序由实际赛题风险再决定，不在本计划中提前冻结 D36A 与 K230 的开发先后。

- 标明适用硬件和版本；
- 有来源索引；
- 有供电和电平限制；

- 有启动和失效安全说明；

“资料已下载”或“PDF 已转成文本”不等于“文档已完成”。
